# PR #34·#37·#38 + #36 — 위성으로 배포를 넓히다

이 문서는 .9 한 대에서만 돌던 배포를 정산(.158)·원장(.164) 두 대로 넓힌 과정을 다룬다. 이건 단순히 "CD를 하나 더 붙이는" 일이 아니라, 로컬에서는 없던 문제 — 다른 서버에 명령을 보냈는데 응답이 오지 않으면 무슨 일이 일어났는지 모른다 — 를 안전하게 다루는 일이었다. 그리고 그 과정에서 코드를 쓰기 전에 설계를 세 조각으로 다시 나눴다.

## 시작 — 한 슬라이스로 담으려다 실패

ADR-027이 정한 토폴로지는 명확했다: .9의 오케스트레이터(main)가 위성 서버에 HTTP+HMAC 서명 RPC로 배포 명령을 보내고, 위성의 agent가 자기 호스트에서 실행한다. 처음엔 이걸 한 작업(#34+#35)으로 담으려 했다 — 전송, 실행자, 그리고 "응답이 안 오면 자동으로 상태를 조회해 재개하는" 복구 로직까지.

코드를 쓰기 전에 두 리뷰 도구로 설계를 검증했더니 14개의 근본 문제가 나왔고, 그중 다섯이 서로 물려 있었다. 매듭의 중심은 **자동 재개**였다 — "UNKNOWN이면 다시 보낸다"는 로직이 중복 실행·영구 미완·만료된 락으로 재실행 같은 문제를 연쇄로 낳았다. 정지 규칙에 따라 설계를 되돌려 세 조각으로 나눴다(자세한 재슬라이스 근거는 study의 [distributed-deploy-unknown](../../../docs/study/tech/infra-journey/distributed-deploy-unknown.md)에 있다).

## 조각 A — 전송과 실행자, 최소한 (#34)

첫 조각은 "UNKNOWN이면 자동 재개하지 않고 사람에게 올린다"로 좁혔다. 자동 재개를 빼는 것만으로 네 문제가 사라졌다. 남은 것은 안전한 기반이다 — 응답도 HMAC으로 서명해 위조를 막고(가짜 완료뿐 아니라 가짜 미실행→중복 배포까지 차단), 위성에 crash-safe 원장을 둬서 "명령을 접수했으나 실행 결과가 불명"인 상태를 재기동 후에도 UNKNOWN으로 회복하며, 미실행과 UNKNOWN을 `DialContext` 성공 전후로 보수적으로 가른다(연결 전 실패만 미실행, 연결 후 모든 오류는 UNKNOWN).

높음 3라운드 듀얼 리뷰를 거쳤는데, codex가 잡은 것들이 전부 crash·overflow의 미묘한 잔여였다 — 특히 crash-safe 저널의 핵심 불변식을 세 번에 걸쳐 좁혔다(원장 poison → truncate 누락 → 개행 유무 판정). 마지막 근본화가 "디스크에 개행까지 도달한 것만 진실"이다 — 정상 원장은 항상 개행으로 끝나므로, 그렇지 않으면 마지막 write가 미완이라는 확실한 신호이고 그 미완 레코드는 fsync 전이라 버려도 안전하다.

## 조각 B — 실행 중의 권리 확인 (#37)

위성이 원격에서 배포하는 **동안** 그 배포 권리(fencing token)를 계속 쥐고 있는지 확인하는 문제다. 로컬에서는 같은 프로세스가 락과 실행을 다 쥐니 없던 문제다. 위성이 .9의 DB에 직접 붙는 건 계정 경계(DT-10) 위반이라, 위성이 각 mutation 직전에 main에 fence-confirm RPC를 보내 "내가 아직 권리자인가"를 되묻는 역방향 채널로 풀었다.

핵심 장치가 셋이다. **sticky guard** — fence 확인이 한 번 실패하면 영구 denied로 고정해, 실패 후 cleanup이 부르는 down까지 차단한다(미실행 Up 뒤에 기존 프로젝트를 Down하는 사고 방지). **DB 시계 판정** — Go 프로세스 시계로 lease 만료를 비교하면 DB와의 편차로 만료된 락을 유효로 오판하므로, main이 DB 시각으로 한 문장에서 판정한다. 그리고 **정직한 TOCTOU 표기** — fence-confirm과 실제 docker 실행 사이 창은 남으므로(docker는 fencing-aware sink가 아니다), 이건 "완전 봉쇄가 아니라 창을 좁히는 완화"라고 적었다. 게이트웨이 블루-그린이 SCG sink-side로 푼 것과 동급이 아니다.

## 조각 C — 자동 재개, 대가를 알고 (#38)

마지막 조각의 선검증이 놀라웠다 — "이 조각을 하지 말자"에 가까웠다. 위성에서 durable UNEXECUTED가 남는 건 "dispatch가 실제로 돌아 부작용 0으로 거절"(pull 실패·preflight)뿐인데, 이 대부분은 결정론적이라 재실행해도 같은 거절을 재현한다. 실익은 "레지스트리 일시 불통 → 회복 후 성공"이라는 좁은 창 하나뿐이다. 게다가 자동 재개는 조각 A의 멱등 판정("같은 requestId 재수신 = 재실행 없이 상태 반환")을 정면으로 뜯어야 한다.

그럼에도 자동 복구 상태 기계를 완성하기로 하고, 조각 A를 의식적으로 재오픈했다 — 선검증이 그 대가를 코드 전에 명확히 해줘서 무음 부채가 없었다. 핵심은 **attempt 축분리**다: command digest(내용)를 충돌 축으로, attempt를 재개 축으로 분리해 "네트워크 중복 재전송"과 "의도적 재개"를 가른다. replay 방어는 version 추적 대신 조각 B의 nonce 패턴을 재사용해 main이 상태를 durable하게 안 들고도 재기동에 안전하게 했다.

## #36 — 실서버에서 켜다

코드가 완성되고 세 서버에 배선했다. 이 과정에서 앞서 만든 계약들이 실서버 boot에서 하나씩 fail-closed로 작동하는 걸 봤다 — 조각 C의 lease 하한이 ".9의 lease 6분이 재개 사이클 12분을 못 덮는다"며 기동을 거부했고(13분으로 올려 해결), compose-embed의 workspace 배타성이 "0700이 아니다"라며, dispatch 배선이 "COMPOSE_FILE도 함께 필수"라며 거부했다. 이 거부들이 배선 세부를 순서대로 지도해줬다 — 계약이 문서가 아니라 실행 가능한 안전장치라는 증거다.

뜻밖의 단순화도 있었다: 이미지가 public이라 DO-9가 대비했던 "호스트별 GHCR pull 자격(토큰)" blocker가 실무상 없었다. 위성이 자격 없이 이미지를 받는다.

배선이 끝나고 정산·원장을 실제로 배포했다 — CD → main(.9) → 서명 RPC → 위성 → fence-confirm HELD → pull·up. 양쪽 컨테이너가 healthy로 떴고 applied 원장이 승격됐다. fence guard가 STALE을 내지 않고 배포가 완주했다는 건 fence-confirm 왕복이 실서버에서 성공했다는 증거다. "위성 배포·롤백 실행 불가"(CDT-1)로 오래 남아 있던 칸이 닫혔고, 배포 대상 넷(코어·정산·원장·게이트웨이)이 전부 실동작한다.

## 남은 교훈

이 여정이 남긴 두 가지. 첫째, **모른다는 것을 상태로 만들어야 한다** — 원격 실행에서 "성공 아니면 실패"라는 이분법은 가장 흔한 사태(응답 유실)를 빠뜨린다. 둘째, **똑똑한 복구는 단순한 안전장치 위에서만 안전하다** — 자동 재개는 그 아래 기반(멱등 원장·권리 확인·시간 예산)이 다 선 뒤에야 얹을 수 있고, 그 전에는 "모르면 사람을 부른다"가 옳은 기본값이다. 이 판단을 코드 전에 두 번의 선검증으로 내릴 수 있었던 것이 이 축의 값이다.
