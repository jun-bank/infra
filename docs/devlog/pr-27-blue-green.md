# PR #27 — 블루-그린 전환 실행

이 문서는 배포가 green 기동·헬스까지만 하던 것을 실제 라우트 전환·드레인·구 슬롯 종료(CD-4 ⑤⑥⑨)까지 완주시킨 과정을 다룬다. 전환 수단(SCG 라우트)은 ADR-031이 이미 확정했고, 이 PR은 그 위에 실행을 얹는다. 핵심 난점은 "전환은 DB 밖 부작용"이라는 데 있었고, 리뷰가 그 부작용의 실패 처리를 통째로 뒤집었다.

## 문제와 원인 — 별개 부작용 사이의 창

배포 창 락은 DB에 있고 라우트 write는 게이트웨이에 있다. 단계 직전에 락 보유를 재확인해도, 재확인과 SCG write 사이의 창에서 lease를 잃은 낡은 실행자의 write가 최종 라우트로 남을 수 있다. 그래서 설계(ADR-031 BG-4)는 fencing token을 검증하는 곳이 자원(sink) 쪽이어야 한다고 정했고, 이 구현은 게이트웨이 전환 API가 token을 검증하는 sink-side 방식을 택했다.

전환 수단 자체의 대안은 ADR-031이 이미 기각해 뒀다 — 큐 기반 라우팅(핫패스에 상시 큐 홉), 엣지 nginx(공유 엣지를 매 배포마다 건드리는 반경), compose 포트 스왑(라우팅 결정이 두 곳으로 흩어짐). 구현 완주 뒤 사용자가 "서비스별 nginx" 방식을 다시 물었을 때의 답도 기록에 있다 — nginx reload가 드레인을 내장한다는 장점은 인정하되, fencing 검증을 sink에 둘 수 없다는 점(conf를 쓰는 쪽이 곧 실행자라 거부할 지점이 없다)이 결정적이었다. 실서버 무중단 관측이 이미 SCG안을 실증한 뒤였다.

## 채택 — 정리는 미전환이 보증됐을 때만

블루-그린은 target=core에만 성립한다 — 슬롯 배선과 게이트웨이 라우트가 core 하나에 결박돼 있기 때문이다. 대상을 안 보고 이 경로로 들어오면 다른 서비스 이미지가 core 슬롯을 덮고 그 위로 core 라우트가 전환되는 치명 경로가 열린다:

```go
// internal/deploy/dispatcher.go:176-199 (발췌) — 대상 결박
case m.Target == TargetCore:
    return d.dispatchBlueGreen(ctx, imageRef, token, plan)
case m.Target == TargetGateway:
    return d.runSinglePath(ctx, imageRef, plan)   // 자기 전환 불가 — 재기동 교체
default:
    // 조용히 core 슬롯으로 흘려보내지 않고 시작 전에 요란하게 거절한다(부작용 0).
    return StateUnexecuted, fmt.Errorf("... target=%q ... fail-closed · 대상 뒤바뀜 방지", m.Target)
```

## 리뷰가 뒤집은 것 — 실패의 보증 계약

이 PR의 하이라이트는 ⑤ 실패 처리다. 최초 구현은 전환 실패(409든 500이든 전송 실패든)를 일괄 "미전환"으로 접고 green을 정리(down)했다. 리뷰가 이것을 치명으로 잡았다 — 409는 소유권 상실 신호인데, 그 순간 내려가는 슬롯은 새 소유자(승자)가 방금 올린 라이브 슬롯일 수 있다.

1차 처방("정리 전 라우트 재조회")은 codex 감사에서 다시 기각됐다 — 재조회도 registry 기준이라 실상태 보증이 아니다. 최종 해법은 게이트웨이가 실패 응답에 보증 수준을 싣고 infra가 그 보증으로 3분기하는 것이었다:

```go
// internal/deploy/dispatcher.go:447-468 (발췌) — 보증 기반 3분기
// - stale(409): 소유권 상실. 승자의 슬롯을 건드리지 않는다(정리 생략) = UNKNOWN.
// - ROLLED_BACK: 라우트가 구 slot 그대로임이 보증됐다 = 올린 slot 정리 = net-0 복원.
// - 그 밖(불명): 정리 금지·UNKNOWN(내리면 트래픽이 가는 쪽을 끊는다).
```

"정리는 미전환이 보증됐을 때만 한다"가 원리다. 이 계약으로 ADR-031이 v1.2로 개정됐다. 그 밖에 리뷰가 바꾼 것 — rollback이 fencing token 최고수위를 후퇴시키던 것(slot만 복구·token은 유지), 게이트웨이 재시작이 env로 복귀해 죽은 슬롯을 라우팅하던 것(상태 파일 지속화 + write-ahead 커밋 순서), 예산 합산 전 개별 검증(overflow fail-open 차단), 그리고 post-fix에서 state를 상태 코드와 무관하게 파싱하던 것(502/400 위조 body가 승격 가능 → 500에서만 신뢰)이다.

검증은 실서버 무중단 관측 3회 누계 5,475건 실패 0(양방향 전환 관통)과 부분 실패 1회의 안전 거동(게이트웨이 정지 → 503 + 부작용 0 + 락 해제)이었다. 각 수정을 되돌려 신규 테스트가 실제로 잡는지 확인하는 네거티브 컨트롤도 돌았다.

## 다음으로의 연결

이 PR이 만든 상황이 곧바로 다음 이슈들을 낳았다 — target=gateway가 정식 배포 대상이 되면서 "core 워크플로의 정상 토큰으로 gateway를 배포하는 것을 막지 못한다"가 즉시 문제가 돼 이슈 #28(repo↔target 결박)이 생겼고, ⑨의 락 결박·드레인 실계수·`/internal` 인증이 후속으로 남았다. 슬롯별 compose 파일이 생기면서 "호스트 compose가 낡거나 변조돼도 digest만 맞으면 통과"의 표면이 오히려 넓어진 것도 #19(compose 동봉)를 재촉했다.
