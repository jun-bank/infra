# PR #31 — compose 동봉 실행 결박: S2의 마지막 조각

이 문서는 S2에서 가장 오래 열려 있던 이슈(#19)를 닫은 과정을 다룬다. 이미지는 digest로 내용이 고정돼 있었지만 기동 정의(compose)는 호스트 파일이라, "이미지에서 막은 구멍이 compose에서 다시 열려 있다"는 비대칭이 출발점이다. 이 PR은 그 compose를 서명 manifest에 동봉하고 검증된 바이트로만 실행하게 만든다 — infra는 수신·검증·실행 측이고, core#3·gateway#9가 발행 측이다.

## 문제와 원인

이슈 본문이 문제를 정확히 잡았다: 두 값(compose revision·config version)이 비어 있지 않은지만 검사하고 이후 쓰이지 않아, 호스트의 compose가 낡거나 변조돼도 이미지 digest만 맞으면 배포가 COMPLETED로 통과한다 — 이미지는 고정되는데 기동 정의는 고정되지 않는 갭이다.

구현에 들어가며 하위 문제들이 드러났다. 기존 `ParseManifest`는 표준 JSON 언마샬이라 미지 필드를 무시하고 중복 키는 뒤엣것이 이긴다 — 동봉 이전에는 무해했지만 이제는 무시된 필드가 곧 무시된 결박이다. base64는 개행을 건너뛰므로 디코드 성공만으로 같은 바이트가 보장되지 않는다. compose의 보간 표면(`.env` 자동 로드·env 상속·`${X:-y}`)은 전부 서명 밖이다. 그리고 TOCTOU — 검증한 파일과 실행되는 파일 사이의 창인데, 블루-그린에서는 이 창이 분 단위다(검증은 bind 시점, 사용은 기동·헬스·전환·드레인을 전부 지난 뒤의 down).

## 채택 — 2분법·strict YAML·세대 workspace·실행 결박

manifest는 embedded(composeContent + appService + composeRevision)와 legacy로 갈리고, 판정은 값이 아니라 키의 존재로 한다(null이 디코드하면 빈 문자열이라 부재와 구별되지 않는다). 검증기는 `yaml.Node`를 직접 순회하며 문서 1개·서비스 정확 1개·닫힌 키 목록·앵커/병합/태그 거절·`$` 전면 금지(정확 일치 2예외)를 강제한다 — 검증기와 compose가 같은 구조를 보게 하기 위해 typed struct에 위임하지 않는다.

```go
// internal/compose/validate.go:255-281 (발췌) — $ 전면 금지가 필드 검증보다 앞선다
// checkNoInterpolation은 디코드된 모든 스칼라(값과 키)에서 $를 금지한다. 면제는 완전일치
// 2형식(${이미지변수}, ${DEPLOY_HOST_PORT}:8080)뿐이다.
// 디코드 후 값을 보는 것이 핵심이다: 원문 바이트 스캔은 "\x24" 같은 YAML 이스케이프를
// 놓치지만, 디코드 후 값은 compose가 실제로 볼 문자열 그대로다.
```

workspace는 candidate를 해시 명명 파일(`compose.sha256-<full64hex>.yml`)로 O_EXCL 기록 후 재해시하고, 배포 성공 후에만 target 단위 `applied.json`으로 승격한다. subprocess env는 금지 목록이 아니라 허용 집합(PATH + 주입값)이다 — "빈 슬라이스면 상속"이라는 암묵 규칙은 주입값이 없는 순간 격리를 무음으로 풀기 때문이다.

## 4라운드 리뷰 — 설계를 좁히고, 실행을 굳혔다

stakes 높음이라 설계 선검증 3라운드가 먼저 형태를 대폭 협소화했다 — 서비스를 정확히 1개로(사이드카는 digest 미결박·replica 문제를 통째로 데려온다), 보간을 `$` 전면 금지로, 회전을 원자 인덱스로, environment를 값 없는 pass-through로. 설계가 코드 한 줄 쓰기 전에 여러 번 뒤집힌 셈이다.

구현 후 듀얼 리뷰가 4라운드를 돌았다. 1회차의 BLOCKER 하나가 특히 교훈적이다 — 승격 판정을 compose revision만으로 하면, 같은 compose에 새 이미지를 올리는 정상 배포의 대다수를 "같은 것"으로 보고 승격을 통째로 삼킨다. 복원 재료가 옛 이미지에 머문다:

```go
// internal/compose/workspace.go:540-563 (발췌) — 승격은 record 상태로 판정
// ⚠️ revision만 비교하면 안 되는 이유(리뷰 E-1): compose 정의는 릴리스마다 바뀌지 않는다.
// 같은 compose에 새 이미지를 올리는 것이 정상 배포의 대다수인데, revision 비교는 그 전부를
// "같은 것"으로 보고 승격을 통째로 삼킨다 — 그 목록을 보고 복원하면 예전 이미지가 뜬다.
```

E-7의 TOCTOU가 3·4회차의 주제였다. 재검증 시점을 뒤로 미루는 것으로는 창이 좁아질 뿐 없어지지 않으므로, **검증한 바이트 자체를 별도 파일로 굳혀 실행기에 결박**하는 방식으로 갔다:

```go
// internal/compose/workspace.go:221-232 (발췌)
// 검증한 바이트 자체를 별도 파일로 굳혀 실행기에 결박하면, 원본이 그 뒤 어떻게 바뀌든
// 실행되는 내용은 검증된 것 그대로다.
```

마지막 라운드의 5건 중 3건은 하드닝으로 수정(스냅샷 재사용 시 symlink 거절·tmp `.env` 부재 단언·잔존 스냅샷 sweep)하고, 2건은 위협 경계 판정으로 종결했다 — 스냅샷 파일 자체의 덮어쓰기는 공존-쓰기자(신뢰 경계 밖)의 문제이고, 동시 dispatch는 배포 창 락이 이미 직렬화한다. 뮤테이션 14종 전부가 대응 테스트를 붉어지게 하는 것도 확인했다.

브랜치 위생 사고도 하나 있었다 — 워커의 `git add -A`로 세션 상태 파일이 커밋에 혼입됐고(미push), 히스토리 재작성으로 정리한 뒤 바이너리를 재빌드·재검증했다.

## 실전 e2e

머지 후 실전 CD에서 5종 중 3종이 실행됐다. green 컨테이너의 compose 라벨이 workspace 세대 파일을 가리키는 것으로 실행 결박이 실증됐고(①), 2차 배포에서 applied가 회전해 새 이미지가 새 record로 승격되며 이전 것이 previous로 보존됐다(⑤ — 1회차 BLOCKER 시나리오의 실전 해소). 무동봉 legacy manifest는 HTTP 422로 거절됐고(④), 동일 상태 재배포는 멱등하게 처리됐다. 나머지 2종(파일 변조·allowlist 밖 compose)은 테스트 계층 커버로 종결하고 사유를 기록했다.

## 다음으로의 연결

#19가 닫히며 S2가 완주됐다 — 배포가 실행할 compose가 서명에 동봉되고, 무동봉 manifest는 422로 거절된다(호스트 파일 실행 경로 철회). ADR-030이 v1.3으로 "compose 부분 구현됨"이 되면서 TOCTOU가 스냅샷 결박으로 구조적으로 닫혔음을 명문화했다. 남은 반쪽은 config다 — manifest의 configVersion은 아직 고정 문자열이고, ConfigVersion 결박(#19-config)은 별건으로 남아 있다. compose는 내용 결박(sha256), config는 버전 단언 결박이라는 강도 차이를 ADR이 정직하게 적어 둔 자리다.
