# PR #29 — repo별 allowlist·repo↔target 결박

이 문서는 배포 대상이 넷이 되면서 생긴 구멍 — 등재된 어느 repo든 어느 target이든 배포할 수 있게 되는 것 — 을 닫은 과정을 다룬다. 이슈 본문의 한 문장이 문제를 요약한다: "결박이 없으면 확장이 곧 구멍이다." stakes 높음이라 설계 선검증·blind 테스트·듀얼 리뷰 3층으로 검증했고, 그 각 층이 서로 다른 것을 잡았다.

## 문제와 원인 — 인증과 인가가 분리되지 않았다

그때까지 게이트 2의 저장소 정책은 단일 env 하나였다. 배포 대상이 하나일 때는 "우리 파이프라인에서 왔다"(인증)가 "무엇을 할 수 있다"(인가)와 같았지만, 넷이 되는 순간 갈라진다 — core 워크플로의 정상 토큰으로 gateway를 배포하는 것을 아무것도 막지 못한다.

설계상의 진짜 난점은 결박을 어디에 두느냐였다. 게이트 2는 진입 층이고 manifest를 파싱하지 않는데, 대조하려면 manifest.target이 필요하다. 최초 설계는 coordinator가 파싱 직후 대조하는 것이었는데, 그것이 선검증에서 뒤집혔다.

## 채택 — 매칭 키는 수치 ID, 결박 자리는 선점 이전

allowlist의 매칭 키는 수치 repository_id다 — 이름은 이전·재생성으로 재사용되지만 수치 ID는 아니다(부분 적재 금지가 이 파일의 태도를 보여준다):

```go
// internal/auth/oidc_allowlist.go:73-111 (발췌)
// 하나라도 성립하지 않으면 부분 적재하지 않고 통째로 거부한다(A4) — 반쯤 읽힌 allowlist는
// "누가 무엇을 배포할 수 있는가"의 절반만 아는 문지기이며, 그 상태로 문을 여는 것이 이
// 경계의 유일한 치명적 실패다.
// 유일성은 셋을 본다: repository_id 중복 · target 중복(1:1) · 이름 중복(ASCII fold 후).
```

결박이 진입 층(멱등 선점 이전)에 놓인 이유가 선검증의 결론이다:

```go
// internal/httpentry/httpentry.go:333-348 (발췌)
// ★ 자리가 여기인 이유: 대조는 **멱등 선점 이전**이어야 한다.
//   - 선점 뒤에 대조하면 권한 없는 요청이 requestId·jti를 소모한다(같은 토큰의 정당한
//     재시도가 재전송으로 취급된다). 여기서 끊으면 부작용이 0이다.
//   - 오케스트레이션에서 대조하면 재전송 경로가 그 층을 지나지 않아 결박이 통째로 우회된다.
//     미들웨어는 모든 경로가 지난다.
```

응답은 정책을 흘리지 않는다 — 403 본문은 일반 문구고, 허용 대상·등재 이름은 이력에만 남긴다(허용 대상을 응답에 돌려주면 토큰을 쥔 쪽이 무엇을 배포할 수 있는지 응답만으로 알아낸다). 사유 코드는 detail JSON으로 영속해 스키마 ALTER 없이 질의된다.

## 세 층의 검증이 각각 잡은 것

**설계 선검증(구현 전)**이 두 치명을 잡아 설계를 뒤집었다. codex와 Opus가 독립적으로 같은 두 곳에 수렴했다 — 결박이 coordinator면 재전송 경로가 그 층을 안 지나 통째로 우회된다는 것, 그리고 단일 env 모드의 "결박 없음 유지"가 무결박 우회 모드를 존속시킨다는 것. 그래서 이 PR의 구조는 코드 한 줄 쓰기 전에 한 번 뒤집혔다.

**blind 테스트**(구현 미열람)는 불변식만 보고 42개 케이스와 명세 공백 5건을 되돌려줬다 — 개명 스쿼팅·타 repo 재전송·교차 경합처럼 악의 우선 케이스를 원본으로 고정했다.

**듀얼 리뷰 루프**는 CD 워크플로의 셸 주입(codex BLOCKER)과 브랜치 미검증(Opus)을 잡았는데, 같은 결함이 core에도 있어 두 repo에 동시 수정이 갔다(core#2가 그 조각이다). 2회차의 N2가 특히 교훈적이다 — 기존 동시성 테스트의 단언 셋이 선언한 실패모드를 통과시키고 있었다(공허 단언). "무엇이 깨지면 이 테스트가 붉어지는가"에 답하지 못하는 단언들을 뮤테이션으로 실제로 붉어지게 교체했다.

## e2e에서 벌어진 일

음성 검증에서 뜻밖의 실증이 나왔다. core repo가 gateway를 배포하도록 allowlist를 임시로 한 줄만 스왑했더니, 1:1 위반으로 agent가 기동 자체를 거부했다("target을 두 저장소가 주장한다" — 부분 적재 금지 코드의 그 문구다). 교차 스왑으로 다시 만든 위반 요청은 HTTP 403 + 이력 `TARGET_FORBIDDEN` + 원장 선점 0행으로 거절됐다 — 결박이 부작용 전에 끊는다는 불변식의 실증이다. gateway의 수치 ID도 추측이 아니라 GitHub API로 실조회했다.

## 다음으로의 연결

이 PR이 세운 것들이 #31로 이어진다 — target을 한 칸만 읽는 부분 디코드(락 이전의 관용 파서)와 락 보유 중의 엄격 파서를 가르는 분업이 여기서 시작됐고, 사유 코드 + detail JSON 패턴도 #31의 여러 코드로 이어진다. 이 작업에서 core repo에도 이슈 체계가 생겼다.
