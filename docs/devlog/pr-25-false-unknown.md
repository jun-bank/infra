# PR #25 — false-UNKNOWN 사건: env 주입 누락

이 문서는 첫 실배포 도중 터진 사건을 다룬다. 이슈에서 태어난 작업이 아니라, 전 파이프라인이 실서버에서 처음 도는 순간에 "배포는 됐는데 배포가 실패했다"는 모순 상태가 나온 것이다. 단계별로 분리해 원인을 확정하는 과정 자체가 이 PR의 본론이라, 별도의 문제해결 문서(troubleshooting-false-unknown.md)가 정본으로 남아 있다.

## 증상 — 모순 상태

응답은 HTTP 409 "원격 실행 UNKNOWN — 사람 개입 필요(락 유지)"였다. 그런데 서버를 보면 요청한 digest 그대로의 컨테이너가 healthy로 떠 있었다. 배포는 성공했는데 agent는 실패로 판정한 것 — 이것이 false-UNKNOWN이다.

## 처음 빗나간 두 해석

문제해결 문서는 오독 2건을 일부러 기록으로 남겼다("같은 함정 방지"). 첫째는 "CI 빌드 실패"였다 — 아니었다. 빨간 X는 이미지 빌드가 아니라 그 다음의 CD 배포-요청 워크플로였고, 두 워크플로를 구분하지 못하면 엉뚱한 곳을 판다. 둘째는 "Spring 부팅 경합"이었다 — 컨테이너 시작과 UNKNOWN 기록 사이가 0.36초뿐이라 그럴듯했지만, 헬스에는 90초 deadline이 있어 0.36초에 끝날 수 없었다. 오독을 깬 것은 새 데이터가 아니라 기존 계약과의 산술적 모순이었다.

## 단계별 격리 — 같은 명령을 손으로 하나씩

agent의 dispatch 순서를 펼쳐 서버에서 똑같이 하나씩 재현하자 원인이 드러났다:

```
STEP 3  up   (CORE_IMAGE 주입) → 컨테이너 Running  exit 0    ← 성공
STEP 4  ps -q (env 없음)       → "invalid compose project"   ← 즉시 실패
STEP 1  down (env 없음)        → 같은 오류        exit 1     ← 즉시 실패
```

근본 원인은 이랬다: 호스트 compose가 `image: ${CORE_IMAGE}`(기본값 없음)인데, Executor는 `CORE_IMAGE`를 `up`에만 주입했다. compose는 어떤 하위 명령이든 프로젝트를 로드할 때 모든 서비스의 image를 먼저 검증하므로, 변수가 비면 프로젝트 자체가 무효가 되어 명령이 컨테이너를 건드리기도 전에 실패한다. 그래서 up은 성공했지만 그 뒤 digest 대조(`ps -q`)와 정리(`down`)가 env 없이 돌아 둘 다 즉시 실패했고 — 정리 실패는 계약상 UNKNOWN이다. 0.36초의 정체도 풀린다: 두 명령이 앱 부팅과 무관하게 같은 config 오류로 즉시 실패한 것이다.

문서의 판정 문장이 사건의 성격을 정확히 규정한다: **로직은 계약대로 동작했고, 입력(compose 명령이 성립하지 않음)이 틀렸다.** fail-closed는 옳게 작동해서 잘못된 "완료"로 위장되지 않았다.

## 부수 결함 — 진단을 막은 관측 공백

원인 규명이 오래 걸린 이유는 dispatch 오류가 어디에도 안 남았기 때문이다. agent 로그는 기동 한 줄뿐이고, DB의 detail 컬럼은 NULL이었다 — coordinator가 UNKNOWN 분기에서 "invalid compose project"라는 정확한 단서를 버렸고, 이력 이벤트에 detail 필드 자체가 없었다. "사람 개입 필요"라면서 정작 사람에게 줄 단서를 안 남기는 것 — 원인과 별개로 고칠 값어치가 있는 결함이었다.

## 검토한 선택지와 채택

이 PR은 대안이 명시적으로 기록되고 기각 사유까지 남은 드문 자리다. 근본 결함에 두 안이 있었다 — A-1(agent가 모든 compose 하위 명령에 image env 주입)과 A-2(compose 파일에 `${CORE_IMAGE:-placeholder}` 기본값). A-1이 채택됐다: 이미지 주입은 agent의 책임이고, fallback 이미지가 파일에 새지 않아 digest 고정 원칙이 흐려지지 않는다.

```go
// internal/dispatch/dispatch.go:112-119 (발췌) — placeholder 상수에 사건의 결론을 박았다
// 이 명령들은 기존 컨테이너를 프로젝트 라벨로 다루므로 image 값 자체는 실행에 쓰이지 않는다 —
// 파싱만 되면 되고, pull되지 않을 값으로 두어 오용을 눈에 띄게 한다. up은 별도로 실제 pinned
// digest를 주입한다(digest 고정은 up이 늘 실주입하므로 유지된다).
const composeImagePlaceholder = "noncreate.invalid/unused:noncreate-ops-only"
```

## 리뷰가 스스로 만든 치명 결함

관측 공백을 메우려고 detail을 쓰기 시작했는데, 리뷰(codex)가 그 수정이 새 치명 결함을 만들었음을 잡았다 — detail 컬럼은 JSON 타입이라 평문을 그대로 바인딩하면 MySQL이 INSERT 전체를 거부한다. 하필 실제 UNKNOWN이 발생하는 순간에만(정상 경로는 detail이 비어 안 걸린다) 이력이 통째로 유실되고 재전송이 재실행될 수 있었다. 실 컬럼에 롤백 트랜잭션으로 재현해 확인한 뒤 JSON 인코딩으로 고쳤다.

최종 검증은 실서버 e2e였다 — agent 재빌드·재배포 후 전 파이프라인(push→CI→GHCR→서명요청→게이트1·2→모드→락→pull→up→verify→헬스→완료)이 HTTP 200으로 그린. 첫 무결 실배포다.

## 다음으로의 연결

이 사건의 교훈이 그대로 다음 작업의 입력이 됐다 — "통합에서 처음 실행되는 명령"은 단위 테스트가 못 잡는다. dispatch는 리뷰 3루프를 거쳤지만, 실제 compose 파일 + 실제 env 주입 경로는 이번이 처음이었고, up만 env를 주고 나머지는 안 주는 비대칭은 실환경에서만 드러났다. 그리고 이 세션에서 부수 사고가 하나 더 발견됐다 — 모델 역할에 대한 사용자 질문을 계기로 ADR-031/032의 듀얼 리뷰 누락이 드러나 소급 리뷰가 실행됐고, 그 자리에서 역할 분담(설계·문서는 메인, 실 구현은 워커)이 확정됐다.
