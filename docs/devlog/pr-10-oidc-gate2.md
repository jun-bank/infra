# PR #10 — 게이트 2: OIDC claim 검증 행렬

이 문서는 "HMAC이 통과해도 누가 보냈는지는 모른다"는 문제를 닫은 과정을 다룬다. 아무 저장소·아무 워크플로에서 발급된 GitHub OIDC 토큰도 형식상 유효하다 — 그래서 게이트 2는 토큰의 서명을 검증한 뒤 claim을 행렬로 대조해 "우리 파이프라인에서 왔는가"를 판정한다. 이 PR의 설계적 핵심은 **무엇을 보지 않기로 했는가**에 있다.

## 문제와 원인 — sub 하나로 판정하면 조용히 무너진다

GitHub OIDC의 `sub` claim은 저장소·ref 등을 합성한 문자열이라, 그대로 문자열 비교하면 형식이 바뀔 때 조용히 통과하거나 조용히 거절된다. 그래서 설계(ADR-027 DO-11)는 sub를 "대조 대상이 아니라 파생값"으로 규정하고 구성 요소를 각각 본다. 코드가 그 결정을 판정 함수 머리에 못박았다:

```go
// internal/auth/oidc.go:317-318
// ★ sub는 검사하지 않는다(DO-11 각주). claims.Subject는 위 칸들의 합성일 뿐이라
// 대조하면 형식 변화에 조용히 무너진다 — 구성 요소를 각각 본 것으로 판정이 끝난다.
```

행렬의 칸마다 "왜 이 칸인가"가 있다. 발급자(iss)는 다른 발급자의 유효 토큰을 막고, audience는 우리 배포 전용 값이어야 한다(플랫폼 기본값이면 다른 목적의 토큰이 배포에 재사용된다). 저장소는 이름과 **수치 ID를 함께** 본다 — 이름은 이전·삭제 후 재생성으로 재사용될 수 있지만 수치 ID는 재사용되지 않는다. `job_workflow_ref`는 같은 저장소의 다른 워크플로가 토큰을 받아도 배포하지 못하게 하고, `jti`는 부작용 전에 선점된다(토큰 재사용 = 재전송).

## 채택 — 서명 검증과 행렬을 두 조각으로

JWT 서명 검증은 직접 구현하지 않고 정평 있는 라이브러리(golang-jwt)에 맡기되, claim 판정은 라이브러리에 맡기지 않았다 — `WithoutClaimsValidation()`으로 명시적으로 끄고, 모든 claim 대조를 `checkClaims` 한 곳이 소유한다(단일 출처). 알고리즘은 RS256으로 고정해 `"alg":"none"`·대칭키 혼동 공격을 이중으로 막았다(타입 검사 + `WithValidMethods`).

실제 JWKS 공개키 페치는 이 PR의 범위 밖이다 — 스캐폴드 뒤에 두고, 키를 얻지 못하면 게이트 2가 fail-closed로 전건 거절하는 상태를 의도적으로 유지했다. 운영 승인 결박도 정직하게 미뤘다: 플랫폼에서 environment 보호가 실제로 서는지는 문서로 판정할 수 없으므로, 판정 전까지 "운영 승인은 자기 신고"라는 사실을 이력에 남긴다(`OPERATIONAL_APPROVAL_SELF_REPORTED`).

## 리뷰가 만든 코드 — absent와 invalid는 다르다

듀얼 리뷰에서 2건이 코드를 바꿨다. 첫째는 **malformed nbf의 무음 통과** — codex가 잡았고, 같은 자리를 Opus는 통과로 봤다. 수치가 아닌 `"nbf":"invalid"`가 0으로 치환되고, 0이면 검증을 생략하므로 서명된 형식 오류 토큰이 거절되지 않았다. 수정은 "키 부재"와 "존재하나 형식 오류"를 구분하는 것이었다:

```go
// internal/auth/oidc.go:247-267 (발췌)
// malformed는 키가 존재하나 수치가 아님을 나타낸다 — 이때 0으로 무음 치환하지 않고
// 거절 대상으로 표시해야 한다(있는데 형식 오류 → 거절 · absent와 구분).
func mapUnix(mc jwt.MapClaims, key string) (seconds int64, malformed bool) {
    raw, ok := mc[key]
    if !ok {
        return 0, false // 부재 — 무음 스킵이 아니라 "없음"이다
    }
    ...
}
```

둘째는 **audience 포함 검사** — "전용값"을 정확 일치가 아니라 포함 관계로 검사해, 우리 값에 다른 audience가 섞인 다중 aud 토큰도 통과했다. 배열이면 원소가 정확히 1개이고 그 값이 우리 audience여야 한다로 좁혔다.

그리고 codex가 High 하나를 함께 냈다 — 운영 배선이 항상 오류를 반환하는 스캐폴드를 쓰고 있어 모든 정상 토큰이 401이 된다는 것. fail-closed 자체는 맞고 agent가 아직 미배포라 안전하지만, 실제 JWKS 페치를 출시 차단 사항으로 이슈 #11에 남겼다. 검증은 claim 칸별 거절 red-first 전체(11칸), sub가 달라도 통과하는지(대조하지 않음의 확인), 합성 RSA 키로 서명 경로 3종이었다.
