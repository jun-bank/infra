# jun-bank/infra

이 저장소는 jun-bank의 저수준 인프라 도구를 담는다: 인증된 요청을 세 홈랩 호스트 중
하나에서 실행 중인 컨테이너까지 이르게 하는 프로그램들이다. 의도적으로 작다. 은행의
도메인 — core, settlement, ledger, batch, reconciliation — 은 다른 곳에 있고
Kotlin/JVM에 머문다; 여기의 어떤 것도 money 데이터를 건드리거나 비즈니스 결정을
해석하지 않는다. 이 저장소의 도구들은 컨테이너, 프로세스, 파일, 그리고 하나의 락 행을
움직일 뿐이며, 그 경계가 핵심의 전부다(ADR-028 §4, ADR-027 DO-4).

## 왜 존재하는가

릴리스 설계는 단일 배포 경로로 귀결되었다: 지속적 통합이 이미지를 빌드하고 요청을
서명하며, Oracle 엣지가 그것을 판단하지 않고 전달하고, 그 엣지 뒤의 한 agent가 이미
존재하는 SSH를 통해 세 호스트에 변경을 적용한다. 사람이 서버에 로그인해 손으로 뭔가를
바꾸지 않는다. 그 단일 경로가 "배포 이력이 곧 사실"을 정직하게 유지한다 — 다만 agent,
그것이 이야기하는 SSH forced-command, 그리고 그 마지막 실패 분기를 잡아내는 감시자가
모두 같은 계약으로 지어져야만 작동한다. 이 저장소는 그 세 프로그램과 그것들이 읽고 쓰는
배포 스키마다.

두 가지 속성이 load-bearing이며 먼저 밝혀둘 가치가 있다. 첫째, 두 개의 게이트가 있고 그
순서는 고정이다: 요청의 HMAC 서명과 OIDC 신원은 어떤 SSH 전송이 열리기 *전에* 검증되므로,
검증에 실패한 요청은 절대 호스트에 도달하지 않는다(ADR-027 DO-2). 둘째, 지속적 사실의
원천은 agent의 파일이 아니라 공유 MySQL 클러스터의 스키마다 — 배포 윈도우 락,
요청/멱등성 ledger, mode, history가 모두 거기 살기에 "락을 획득하고, 요청을 예약하고,
mode를 확인하고, 결과를 기록"하는 것이 하나의 트랜잭션일 수 있다(ADR-022 DT-9,
ADR-027 §2.2). agent의 로컬 저장소는 캐시이며, 정확히 하나의 예외가 있다: watchdog이
읽는 자기 교체 의도로, watchdog이 DB 계정을 전혀 필요로 하지 않도록 로컬에 남는다
(ADR-027 DO-19).

## 구조

- `cmd/agent` — deploy-agent. 엣지의 LAN 측에서 CI 요청을 받고, 두 게이트를 실행하고,
  배포 윈도우 락을 획득하고, CD-4 시퀀스를 적용하고, SSH로 위성 호스트에 도달하고, 자기
  교체를 위해 자기 자신을 원격 대상으로 취급한다(ADR-027 DO-2, DO-3, DO-8).
- `cmd/dispatcher` — root 소유의 SSH forced-command. SSH는 셸이 아니라 이 프로그램에
  도달한다. 고정된 열거형 인자 집합을 받아들이고 그것들을 구조적으로 파싱한다; 권한을
  낮추는 것이 아니라 입력의 자유도를 낮춘다(ADR-027 DO-13).
- `cmd/watchdog` — 허브에 상주하는 감시자. 로컬 자기 교체 의도를 읽고, 데드라인이
  지나도록 완료 표시가 없으면 이전 manifest를 정확히 한 번 재시작한다. 어떤 요청도 받지
  않으며 DB 계정을 보유하지 않는다(ADR-027 DO-19).
- `internal/auth` — 게이트 1: HMAC 서명, 신선도, 멱등성, 그리고 OIDC 클레임 매트릭스
  (ADR-027 DO-2, DO-10, DO-11).
- `internal/ssh` — 게이트 2: 호스트별 키와 host-key 고정을 갖춘 SSH 전송, 그리고 세 가지
  원격 실행 상태(ADR-027 DO-3, DO-14, DO-16).
- `internal/deploy` — CD-4 적용 시퀀스와 서명된 manifest(ADR-027 DO-4, DO-18).
- `internal/store` — 배포 스키마에 대한 유일한 관문. 모든 락 변경은 저장 프로시저 전이를
  거치며; history는 append-only다. 이 패키지는 일반 DML 메서드를 노출하지 않으므로, DB
  grant에서 금지된 것과 마찬가지로 코드에서도 raw 쓰기가 불가능하다(ADR-022 DT-12).
- `deploy/schema` — 배포 스키마 DDL: 단일 행 락 테이블, append-only history와 ledger,
  일곱 개의 락 전이, 그리고 두 개의 계정 grant(ADR-022 DT-9부터 DT-12까지).

## 빌드

`make build`는 모든 것을 컴파일하며 주 게이트다 — 모든 커밋은 `make vet`과 함께 이것을
green으로 유지한다. `make test`는 테스트 스위트를 실행한다; 실제 MySQL에 대해
(Testcontainers를 통해) 배포 스키마 프로시저 계약을 검증하는 통합 테스트는 현재
골격인데, 트랜잭션 경계와 원자성 주장은 인메모리 대체물이 아니라 오직 실제 데이터베이스에
대해서만 검증될 수 있기 때문이다(test-strategy L1 하한). `make lint`는 runner에서 사용
가능할 때 golangci-lint를 실행한다.

설정과 시크릿은 절대 커밋하지 않는다. `.env.example`을 `.env`(gitignore됨)로 복사하고
서명 키, OIDC 기대값, 호스트별 SSH 주소와 키, 그리고 배포 스키마 연결 문자열을 채운다.

## 정본

이 코드가 구현하는 계약은 `docs` 저장소의 아키텍처 결정 기록(ADR)이 소유하며, 이 코드는
그것들을 재해석하지 않는다:

- **ADR-027** — 배포 오케스트레이션(DO-1부터 DO-20까지).
- **ADR-024** — 릴리스 전략(블루-그린, mode, 긴급 롤백 override).
- **ADR-022** — DB 토폴로지(배포 스키마, 두 계정, 그리고 프로시저 전용·append-only 권한 모델).
- **ADR-028** — 언어 선택(인프라 계층이 Go인 이유).
